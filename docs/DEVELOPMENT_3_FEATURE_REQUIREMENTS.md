# Mistbell 3.0 独立功能重建清单

> 本文以 `codex/mistbell-development-3.0` 的基线提交 `ba2ae9b3099fa7282ab58b35b2128f9bca89b1ee` 为起点。
>
> **隔离规则：** PR29 及其后续支线只提供产品需求和经验，不作为本支线的代码来源。不得从旧支线 cherry-pick、合并或直接移植实现；不得把旧支线报告的问题未经验证就认定为本基线的缺陷。所有实现与测试均针对 3.0 基线重新设计。

## 不可丢失的功能目标

1. **向量记忆**：可靠的语义存储、检索、命名空间隔离、缓存、并发与错误恢复；向量空间身份必须明确，不能混用不同模型产生的向量。
2. **本地 Embedding**：设备端推理与可配置的本地模型方案；清楚报告实际使用的后端。NPU/GPU/CPU 状态必须来自真实执行结果，不得用装饰性提示冒充成功。
3. **独立记忆整理模型**：聊天模型与记忆抽取/整理模型配置可独立设置，支持各自的 Base URL、密钥、模型、超时和失败处理。
4. **事实历史**：事实变化时保留可追溯的历史记录，明确当前事实、旧事实、时间和来源；避免静默覆盖或错误地同时注入互相矛盾的事实。
5. **世界书递归扫描**：可控制递归扫描开关、深度、扫描文本范围与预算；正确处理常量条目、关键词、递归激活、去重和循环引用。
6. **生图 API**：独立的图像生成配置与调用链，安全处理密钥、请求/响应、下载大小、文件类型、预览与失败重试。
7. **Token 与缓存优化**：减少无效上下文与重复信息，同时稳定可缓存的提示词前缀；动态内容与静态内容分层。节省量和缓存命中改善必须通过可重复测量证明，不预先承诺数字。
8. **Mistbell 专属内容格式引擎**：为世界书和角色卡定义版本化的原生格式与语义，兼容读取常见旧格式；保留未知字段和原始导入内容，提供可解释的导入诊断，避免无意破坏用户文件。
9. **验证与交叉审核**：常规 CI 以编译、单元测试、静态检查为主，不例行打包 APK 或启动昂贵的模拟器流程；最终集成阶段才执行完整 Android/Room/打包验证。两个独立模型必须审查同一个不可变 SHA，并记录模型实际调用、SHA 和结果；任何一方未执行或失败都不能宣称双审通过。

- 结构化记忆与抽取：`StructuredMemoryEntity.kt`、`StructuredMemoryDao.kt`、`StructuredMemoryRepository.kt`、`service/MemoryExtractionService.kt`。

## 实施原则

- 先验证基线现状，再决定保留、重构或新增；不得仅凭文件名判断功能完成。
- 先定义模块契约和数据模型，再并行开发低耦合模块。
- 每个功能以用户可观察的行为和回归测试验收，而不是照搬旧支线修复列表。
- 数据迁移必须非破坏性；无法证明旧数据属于哪个 Embedding 空间时，不得静默混用或删除。
- PR 保持 Draft，直到功能、测试、双模型交叉审核和最终验证均有证据；未获明确授权不得合并。

## 必须明确纳入：EmbeddingGemma 2 与 Redmi K70 Pro 专项

这是已确认的硬性目标，不是可选的“以后再说”：

- 目标设备：**Redmi K70 Pro / Qualcomm Snapdragon 8 Gen 3 / SM8650**；本阶段优先只针对该机型优化，但架构需为未来其他处理器预留后端接口，不承诺其他设备当前已兼容。
- 本地纯文本 Embedding：把 **EmbeddingGemma 2** 作为重点候选，评估可实际部署的模型版本、量化/体积、推理运行时和 Android 集成方式。不能仅因为模型名称或库存在就宣称可运行。
- 设备加速路径：优先验证该设备上真实可调用的 **NPU/Qualcomm 加速后端**，再按能力和可用性回退到 GPU、CPU。必须记录每次实际选择的后端和失败原因；若 NPU 不可用，要明确显示回退结果，不得伪报 NPU 已运行。
- 版本兼容：为较新但无法在目标设备/运行时运行的模型版本保留可配置的兼容版本/回退选择。回退前验证模型、tokenizer、运行时和向量维度兼容性。
- 运行时与依赖：核实 LiteRT-LM 及实际所需的 Qualcomm/QNN/QAIRT 或其他运行时、ABI、许可、打包体积和设备可用性；只加入已验证必要的依赖，不凭空添加库或假定某个 NPU delegate 可直接工作。
- 向量空间隔离：EmbeddingGemma 2、其他本地模型和远程 Embedding 的向量必须按模型/版本/配置建立独立命名空间。维度相同也不能混合；切换模型后须有安全的重嵌入/重建流程，失败时保留旧数据且不能静默污染索引。
- 维度与检索前缀：模型原生输出维度、可选截断维度（如 768/512/256/128）以及查询/文档任务前缀，必须以所选模型的正式规格和实际运行测试为准；不能把历史设计讨论中的数字直接当作已验证事实。
- 模型下载和更新：支持校验和/完整性验证、下载中断恢复或安全重试、并发去重、存储空间检查和明确的失败提示；不把不完整模型注册为可用。
- 本地优先：Embedding 失败时不得偷偷转成云端请求。是否允许远程回退必须是明确配置，默认行为要符合隐私预期。
- 验收证据：在真实 Redmi K70 Pro 上验证模型加载、文本向量输出、维度/数值有效性、NPU/GPU/CPU 实际后端、冷启动与持续推理、模型切换和失败恢复。模拟器或 CI 通过只能证明对应测试范围，不能替代真实 NPU 验证。

## UI 点击反馈与动画专项

“没有动画”不能直接作为整个 3.0 UI 的结论：基线中已经发现部分动画，例如角色卡使用 `animateFloatAsState` 做缩放，消息气泡使用 `AnimatedVisibility`，聊天顶部栏有高度动画；但也发现列表项只使用普通 `Modifier.clickable`，不能据此认定所有按钮和可点击区域都具有统一、清晰的按压动画。需继续对真实 UI 逐屏盘点。

目标是建立一致且轻量的交互反馈规范：

- 普通点击有可感知但克制的按压/涟漪反馈；卡片可有短促缩放或轻微位移/高程反馈，避免所有元素都做夸张动画。
- 页面切换、展开/收起、弹窗、加载/发送状态与操作成功/失败应有合适的过渡或状态反馈；不能用动画掩盖失败或让用户误以为操作成功。
- 动画时长、缓动和触控反馈保持一致；不影响聊天滚动、输入、长按菜单、无障碍语义或低性能设备。
- 尊重系统动画缩减/关闭设置；避免无意义的无限循环、重组抖动和昂贵的绘制。
- 为关键交互补充 UI 测试或可重复的验收步骤。完成与否应以逐屏清单和真实运行验证为准，而不是只看是否导入了动画 API。

### 用户实测补充：动画生硬、过渡突然（2026-10-16）

用户在真实使用中反馈：当前 UI 动画不流畅，交互表现有明显的突然跳变。此反馈属于已观察到的体验问题；但具体根因仍需逐屏复现，不能在没有性能证据时直接归因于某一个 Compose API。

排查与实现必须覆盖两条独立路径：

1. **过渡设计问题**：状态或页面内容直接替换，缺少合适的进入/退出、展开/收起或按压反馈，造成“突然出现/跳变”。
2. **运行性能问题**：动画过程中掉帧、卡顿、抖动或延迟响应。需检查重组范围、Lazy 列表 key/稳定性、状态读写位置、主线程 I/O/计算、图片解码、过度绘制、动画对象生命周期与无限动画数量等；只有采样或可重复测试支持时，才将某项认定为根因。

验收不能只看代码中是否存在动画 API。应在目标 Android 真机上记录关键交互的复现步骤与前后表现；对页面切换、角色卡点击、消息气泡操作、弹窗、展开/收起和发送/加载状态分别检查。动画应及时响应触摸、过程连续、结束状态准确，不遮掩操作失败，不引入明显额外掉帧；同时验证长按、滚动、输入和无障碍交互没有退化。若暂时无法取得真机性能 trace，应明确标记为“静态检查/模拟验证”，不能声称真实设备流畅度已通过。
