## 1. 审核对象与前置条件

审核前先确认三件事，缺一件就退件：

1. 任务文件（`tasks/` 下的冻结件）确实存在且字段齐全。
2. 声明的 `baseline_commit` 真实存在，且属于 `codex/mistbell-development-3.0` 线。
3. 前置门禁实际跑过（有输出），不是"应该有"。

```bash
python3 lint/collaboration-gate.py --phase pre-review --mode repo \
  --repo . --freeze tasks/<本轮任务文件>.yaml --json
```

## 2. 本门禁能证明什么、不能证明什么（最重要的一节）

`lint/collaboration-gate.py` 当前是**结构化元数据门禁**：

- 能判定：契约完整性、约束 ID 封闭性、引用完整性、状态枚举合法性、冻结字段一致性、受保护路径与 schema 版本存在性。
- **不能**判定：任何行为类约束（`NEEDS_TEST` / `NEEDS_DEVICE` / `NEEDS_HUMAN`）。

因此：

- ❌ 不得因为门禁返回 0 就写"约束全部满足"、"功能已验证"。
- ✅ 必须写"结构门禁通过；行为类 N 条待测试、M 条待真机、K 条待人工裁决"。
- 门禁输出里的 `SKIP` 与 `NOTE` 全部保留在审核记录里，不得省略。

## 4. 允许通过的边界（不得过度阻断）

- MT-004：范围外依赖不得直接阻断本批；应另提变更请求。
- MT-014：只挂起依赖闭包内的模块，独立模块继续。
- MT-011：日常轮次**不得**被追加完整 APK / 全量真机门槛。
- MT-048：不适用项注明理由即可；不得由此自动扩展成每轮全量门禁。
- MT-007：不得要求"独立双模型审核"作为 App 功能通过条件。
- MT-016 / MT-051：只有**最终阶段**才需要完整真机验收矩阵。

## 5. 审核结论格式（必须逐字段给出）

```yaml
review:
  task_id: <与冻结文件一致>
  reviewed_sha: <40 位 SHA>
  gate_output: <pre-review / post-review 的实际命令与结论>
  structural_gate: PASS | FAIL          # 只表示结构门禁
  behavior_verified: false              # 本门禁恒为 false，除非另有测试证据
  adjudication_pending:
    needs_test:  <条目列表或"无">
    needs_device: <条目列表或"无">
    needs_human: <条目列表或"无">
  rejected_items: []                    # 命中 §3 的条目，附依据 ID
  scope_notes: <本轮未做、且不做的事>
```

**禁止表述**：只要行为类档位还有 pending，"通过"之外不得写"已验证"、"功能已完成"、"约束全部满足"。
